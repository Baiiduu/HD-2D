# CPU 与 GPU 性能优化

更新：2026-10-21。正式地图：`demoWithMeowa/1/scenes/world/world.tscn`。

当前验收负载为 **128 只混编怪物、基础剑术、蓄力预览与人物本体弹射**，目标约 100 FPS，尚未达成。AutoFan、满技能与更大怪潮不作为本轮主验收。本文只保留现行方法、有效证据与候选状态；旧实验流水由 Git 历史保留。

## 分开分析，最后合并验收

| 测试方向 | 保持的负载 | 降低的干扰 | 主要看什么 |
| --- | --- | --- | --- |
| CPU 战斗逻辑 | 128 怪、真实 AI／拥挤／墙体碰撞、剑术、预览、弹射 | 优先 headless；需要渲染时使用固定的最低画质与低 3D 分辨率 | 每物理步与每秒 CPU 工作量、显示回调、尖峰、行为正确性 |
| GPU 与画质 | 正式地图、固定镜头、分辨率、待测画面效果 | 零怪或少量怪、无攻击；必要时冻结场景更新 | GPU 帧耗时、渲染 CPU、可见／阴影绘制、画面变化 |
| 完整场景 | 128 怪、完整战斗、约定的目标画质 | 关闭 VSync／帧率上限以测性能余量 | 实际帧间隔、平均 FPS、P95／P99、长时间稳定性与手感 |

**降画质、减怪和冻结都是允许的定位手段。** 同一组前后对照必须使用相同的隔离条件；单次只改被测方案。隔离测试的收益不能直接写成完整游戏收益。用户选择较低画质得到的 FPS 是该画质档的结果，不能标成同画质算法提升。

CPU 还包括渲染剔除、阴影准备和绘制提交。它们归入下文渲染链路分析，和怪物模拟分别计时：GPU 优化可能同时减少渲染 CPU，降低像素量则未必能减少提交成本。

## CPU：先消除 GPU 干扰

### 固定条件与测量

1. 固定 128 只、出生顺序／随机种子、地图版本、动作流程与 60 Hz 物理频率。保留真实导航、怪群密度、墙体碰撞、命中、蓄力和弹射交互；模拟免伤锁血仅用于维持测试数量。
2. 首先用 headless 对照，测 CPU 与行为，不报告 GPU 或显示 FPS。现有工具按站立普攻 180、移动普攻 120、蓄力 120、弹射 240 个物理步采样。
3. 需要查看真实窗口中的 CPU 时，将 3D 分辨率、抗锯齿、阴影和后处理降至同一低档，必要时关闭天气与装饰效果；确认 GPU 不再限制吞吐。保留怪物模拟与实际攻击，不能以减少怪物或取消碰撞代替 CPU 优化。
4. 每个后端使用新进程，先预热，再按旧／新／新／旧交错复测。记录源码／配置哈希、出生布局和行为；排除其它游戏／录屏负载，保持窗口类型、前台状态与电源模式一致。
5. 先做无 profiler 的整体计时，再用 profiler 定位热点；插桩结果单列，不混入最终性能均值。函数包含子调用的时间不能重复相加。

| CPU 指标 | 使用边界 |
| --- | --- |
| `physics_callbacks_ms` | 物理回调窗口，不包含全部物理服务器推进 |
| `physics_span_ms` | 更宽的物理窗口，包含范围以工具实现为准；不再与回调时间相加 |
| `process_callbacks_ms` | 每次显示更新回调，和每物理步成本分别记录 |
| `one_physics_plus_one_process_ms` | 固定 60 Hz 工具的流程比较指标，不是渲染帧时间，不能倒数成 FPS |
| `Performance.TIME_PHYSICS_PROCESS` | 当前引擎的上一秒物理峰值，不当作逐步平均值 |

100 FPS 对应显示帧预算 10 ms，但物理每秒仍推进约 60 步。估算主线程负载时使用 `60 × 每步 CPU 成本 + 目标显示频率 × 每次显示 CPU 成本 + 其它工作`，避免重复计入嵌套窗口。CPU 与 GPU 可重叠，不能把两者耗时直接相加作为帧时间。预算只能筛选方案，最终吞吐必须实测。

### 优化与淘汰标准

优先处理完整链路中重复的地形／形状读取、普通移动与拥挤通行、蓄力判群和预览重算。已有空间网格、共享追击树、邻居复用与对象池，不再把“新增空间划分”当作未经实现的通用答案。

先检查资格、冷却与范围，再做精确查询；缓存须明确失效条件，动态墙体实时生效。集中更新或原生化只有在减少实际工作与数据往返后才有意义；调用数减少、微基准加速或换语言本身不算整场收益。

候选先过碰撞、脱困、密度、命中与弹射门槛，再比较整体 CPU 与尾部耗时。保留旧实现开关；收益很小、阶段退化或行为失败的方案不默认接入。用于定位的关闭 AI／碰撞／预览实验必须标为删减诊断，不能作为优化交付。正式优化不以降低模拟／动画频率、漏伤害或降低裁切精度换成绩。

## GPU：减少战斗负载，保留待测画面

### 固定条件与测量

1. 从 READY 零怪空场开始，人物与相机固定，等待初始化、相机跟随和材质设置收敛。需要研究怪物材质或战斗特效时，只保留可稳定重现的一小组对象与动作。
2. 固定实际输出像素、3D 渲染比例、Style、天气与相机。内嵌窗口、独立窗口和导出包分别记录；同为“全屏”不表示内部渲染分辨率相同。
3. 先测正常更新的基线，再按需冻结更新，逐项检查阴影、抗锯齿、SSAO／SSIL／SSR、体积雾、反射视口与透明叠加。每项采用基线／修改／恢复，给缓存预热时间。冻结会改变动画与阴影缓存，结果只作定位。
4. GPU 测试保留待测画质，不把所有效果一起关闭后宣称某一项加速。低分辨率对照用于识别像素成本；若 GPU 时间下降而帧间隔改善有限，继续检查渲染 CPU、同步或帧率限制。
5. 同时记录活动视口、GPU 时间、渲染 CPU、可见绘制与阴影绘制。先判断限制来自像素计算、重复阴影还是提交，再选择方案；不能仅按灯光数量或 draw call 数排优先级。

完整渲染 CPU 按 `RenderingServer.get_frame_setup_time_cpu()` 加活动视口的 CPU 计时统计；GPU 计时覆盖活动视口，避免只读根视口漏掉反射等工作。视口时间戳异步返回，用预热后的稳定窗口统计，不和当前一帧逻辑强行相加。可见／阴影绘制次数是工作量线索，不等于耗时占比。接口边界见 [Godot RenderingServer](https://docs.godotengine.org/en/stable/classes/class_renderingserver.html#class-renderingserver-method-viewport-get-measured-render-time-cpu)。

### 方案选择

优先减少重复投影、无效光源覆盖和不必要的提交，再优化像素／材质成本。降低分辨率或关闭效果可以成为明确的画质档，但要注明清晰度、漏光、阴影或氛围取舍。合批扩大后可能恶化剔除和阴影覆盖，必须看 CPU／GPU 的净收益，不能只看提交数下降。

画面优化先在空场稳定对照，再加入 128 只与真实战斗，检查怪物投影、特效透明叠加和运镜后的最差视角。画面、全屏切换与手感由人工验收；自动逻辑测试不能代替。

## 当前证据与采用状态

以下是 2026-10-17 的历史源码／地图快照结果，机器为 Ryzen 7 6800H、RTX 3050 Laptop，Godot 4.7.2、D3D12 Forward+。地图随后有编辑，**这些数字不代表当前检出的实时 FPS**，也不能与更早机器或不同配置的结果拼接。

### CPU 证据

| 方案／现象 | 有效结果 | 当前判断 |
| --- | --- | --- |
| 原生纯查询后端 | 128 怪指定 CPU 流程 18.563→17.700 ms，约降 4.65% | World 已选择，身体移动证明仍保留；小幅收益，不能沿用早期约 20% 的局部结果 |
| 集中回调＋预览去重 | 128 怪 18.381→17.307 ms，约降 5.84% | 默认关闭；不能将单项节省相加，尚不足以解决主瓶颈 |
| 原生怪群候选＋集中驱动 | 修复后 128 怪 18.098→14.769 ms，约降 18.39% | 默认关闭；未达此前约 30% 的候选目标，且仍有逐怪入口及脚本回调，并非完整批量内核 |
| 蓄力预览 | 单组关闭提示使 CPU 窗口约 23.2→16.5 ms | 仅作热点线索，正式提示保留，不视为可无代价节省全部差值 |
| 静态／怪物批量绘制候选 | 未证明稳定整场净收益，部分配置更慢 | 保持关闭，不因 draw call 下降就采用 |

普通追击中，人物胶囊的重叠恢复曾把怪物推入低底座。脚本与原生路径已对普通移动使用临时人物碰撞例外；锁线冲锋继续保留真实人物碰撞与伤害。捕获的负例已修复，两组各 84,480 次逐步内胶囊检查未见 3 mm 侵入；这不是对任意布局的保证，后续仍须覆盖薄墙、墙角、动态障碍和持续脱困。

原生候选修复后的真实渲染短测，1440×900、VSync 关闭、128 怪：脚本各阶段约 7.0～7.6 FPS，候选约 11.1～15.5 FPS。样本短，弹射时可见数量有变化，只证明当时完整场景仍远未达标；不能从 CPU 窗口倒数推导该结果，也不能据此断言整场只有 CPU 瓶颈。

### 空场渲染证据

保持零怪与正常更新，独立窗口的完整画面基线：

| 输出分辨率 | 墙钟帧间隔 ms | GPU ms | 渲染 CPU ms，含 setup |
| --- | ---: | ---: | ---: |
| 1440×900，两轮范围 | 12.31～16.54 | 11.49～15.93 | 6.23～7.51 |
| 1920×1080 | 22.00～23.52 | 21.46～22.96 | 6.88～7.33 |
| 1280×800 | 11.56～11.79 | 9.65～9.81 | 6.32～6.49 |

物理回调仅约 0.5～0.6 ms／步，显示回调约 0.6 ms／帧。该空场主要应查 GPU 与渲染提交，而非逐怪模拟。用户报告的不到 40 FPS 来自编辑器内嵌运行，上表未复现该环境，不能把差值全部归因于编辑器。

同一 1440×900 冻结画面的阴影定位：

| 诊断条件 | 渲染 CPU ms | GPU ms | 阴影绘制／帧 |
| --- | ---: | ---: | ---: |
| 完整画面 | 6.46 | 11.64 | 3972 |
| 仅关闭全向补光阴影 | 2.90 | 8.95 | 916 |
| 关闭所有局部阴影 | 2.30 | 8.60 | 685 |
| 每轴 3D 分辨率减半，保留阴影 | 6.19 | 5.66 | 4002 |

这说明全向补光的重复阴影同时增加 CPU 提交与 GPU 成本，降低像素量主要缓解 GPU。它们是隔离诊断，尚不是保持原画面的优化交付。测量时水面专用灯阴影已由既有门控关闭，不重复计算为新收益；没有活动的平面水面镜像视口。极光额外视口约 0.06～0.10 ms GPU，不据此推导它在所有材质中的总成本。

当前已提供分辨率、阴影与其它画质开关，供选择画质档和定位使用。参数说明见 [画质与显示](../technical/parameters-and-styles.md#画质参数的含义)。下述实现已接入，GPU 净收益与同画质验收仍待测量。

### 已接入、尚未测量的特效优化（2026-10-19）

命中碎屑按寿命分批回收 MultiMesh 的过期槽位，并稳定压紧存活实例，保留轨迹、寿命和透明绘制顺序；不再持续提交整场累计历史。保留少量过期槽位以摊薄 CPU 搬移，CPU 镜像数组按原容量固定分配，不读取 GPU 实例缓冲。持续输入用例验证提交规模有界，不据此推导 GPU 耗时或 FPS。

镜头雨滴使用 16×12 候选表，按原编号顺序记录各格可能覆盖的雨滴，每帧独立快照约 3 KiB。覆盖包围原 shader 的 2.5 倍半径早退区域并留一像素舍入余量；真实轮廓、折射、亮光采样与叠加公式保持原样。尺寸与实际 Canvas 输出不匹配时回退原循环，关闭效果停止建表。设屏幕像素数 P、雨滴数 D、格数 T、总登记数 B、每像素候选数 k(p)：原候选检查为 O(PD)，新 CPU 建表 O(T+D+B)、空间 O(T)，GPU 候选检查 O(P+Σk(p))；雨滴全重叠时仍可能退化为 O(PD)，不能将复杂度变化当作已证明的净提速。

自动回归仅检查覆盖、顺序、快照隔离、尺寸变化、启停与实际天气参数绑定；原生 shader 编译后的画面、GPU 成本及完整战斗仍由人工验收。本轮未运行压测或渲染窗口。
