# 仙门灯会·异变 总体设计文档

版本：1.0  
日期：2026年10月10日  
项目：东方幻想像素风 HD-2D 可玩 Demo  
开发基础：本仓库 `benchmark/threejs`，以原项目 `D:\Project\godot\games\benchmark\threejs` 的视觉表现为参考。

本项目制作一个约 5～8 分钟的事件型可玩切片：玩家参加宗门灯会，经历灯火熄灭的异变，通过调查、短战斗和修复灵灯，净化守山灵兽，让灯会重新开始。核心原则是：**先设计一个值得观看的游戏片段，再让玩法服务于这个片段。**

用户已确定开发这个方向。本文作为第一版制作依据；具体名称、时间分配、资产数量、动画规格及性能指标是初版制作目标，随原型验证调整。本文描述目标体验，不代表功能已实现。

## 1 项目定位

### 1.1 一句话概念

一名宗门弟子在灯会之夜修复熄灭的引灵灯阵，救回被污染的守山灵兽，并亲手让山谷重新亮起来。

### 1.2 交付目标

- 一段可以从头玩到结尾、有完整故事和情绪变化的单人 Demo。
- 一个有建筑、居民、活动、环境声和互动的东方幻想宗门。
- 一组能用于教学视频的制作对比与游戏高光镜头。
- 一条可追溯的 Meowa 资产制作流程，覆盖美术、动画、UI、音效和地图素材。

第一版面向桌面浏览器和键鼠操作，延续 Three.js 技术基础。画面采用像素角色、像素场景素材与具有纵深的三维环境、灯光、雾和水面反射，形成 HD-2D 表现。

### 1.3 设计优先级

1. 世界的辨识度和灯会生活感。
2. 异变与恢复带来的视觉、声音和情绪变化。
3. 玩家行动与世界变化之间清晰可感的因果关系。
4. 足以支撑片段的探索、交互、战斗与轻解谜。
5. 可稳定游玩、重试和录制的完整流程。

战斗负责展示动作与反馈；机关负责恢复环境；NPC 负责建立世界印象。各系统围绕事件组织内容。

## 2 世界与故事

### 2.1 地点

宗门建在有瀑布、竹林和溪流的山谷中。弟子住处连接灯会广场，石桥跨过放河灯的河岸，登山步道通向守山灵兽所在的山门。建筑采用青瓦、木柱、石阶、纸灯、旗幡和灵纹。

引灵灯阵平时维持山门结界，也为灯会提供灵光。守山灵兽与灯阵相连，既是宗门的保护者，也是弟子熟悉的伙伴。

### 2.2 事件

玩家来到河岸时，一股异常灵气侵入灯阵。灯笼几乎同时熄灭，音乐中断，河灯逆流，远处山门升起青蓝雾气。失去灯阵保护的守山灵兽受到污染。

玩家调查异常，清除挡路的侵蚀生物，重新点亮三座灵灯。灯阵逐步恢复，限制污染并削弱灵兽。玩家在山门完成短战斗和净化，恢复守护者与灯会。

### 2.3 叙事方式

通过环境变化、少量 NPC 对话和任务提示讲述故事。灯会阶段至少有一位弟子提到守山灵兽，例如“它每年都守着山门，等我们把最后一盏河灯放走。”让净化结局有情感基础。

异变成因保持简洁，不扩展成世界观长篇、派系争斗或后续章节。主角与灵兽的正式名字可在美术定稿时确定。

## 3 完整体验流程

目标情绪曲线：**惊艳 → 悠闲 → 好奇 → 紧张 → 战斗 → 解谜 → 高潮 → 治愈。**

以下时间是一次顺利首通的参考节奏，总长约 7 分钟；允许自由探索，不用倒计时强制推进。

| 阶段 | 参考时长 | 玩家行动 | 主要展示内容 |
| --- | --- | --- | --- |
| 出门 | 30 秒 | 从住处进入灯会 | 夜景第一印象、角色移动、前景与远景 |
| 灯会 | 70 秒 | 逛广场、与 NPC 交谈、到河岸放灯 | 地图、美术、生活动画、对话与摊位 UI、环境音 |
| 异变 | 20 秒 | 目睹熄灯，获得调查目标 | 灯光与雾变化、音乐切断、逆流河灯、事件 UI |
| 遭遇 | 30 秒 | 击退两个侵蚀生物 | 攻击、闪避、技能、受击、VFX 与战斗音效 |
| 灯阵 | 120 秒 | 找灵石、修复三座灯塔 | 轻解谜、交互 UI、三种不同的区域恢复反馈 |
| 山门 | 90 秒 | 战斗并净化守山灵兽 | Boss 动画、预警、镜头反馈、净化高潮 |
| 回程 | 40 秒 | 回到石桥 | NPC 与音乐恢复、河灯与建筑重新亮起 |
| 收尾 | 30 秒 | 看灯会继续，选择重新游玩 | 山谷灯火全景、治愈结局 |

### 3.1 灯会开场

玩家从住处门口开始，立刻能移动。前 10 秒看见清晰的主角、暖灯、近处活动和远处山谷，不先展示长文本或战斗教程。

广场上有练剑、摆摊、喝茶、聊天等小活动；河岸有人放灯。NPC 采用错开的短循环，避免所有人同步动作。练剑角色与围观者、茶客与摊主的位置形成合理关系。

至少安排一次简短对话和一次河岸交互，使玩家在异变前亲自接触世界。摊位浏览为可选互动，不能阻塞主线。

### 3.2 熄灯异变

玩家到达河岸并完成放灯交互后触发一次性事件；具体触发范围在试玩中调整。

事件节奏分为三个清楚的节点：钟声或灵气异响，灯火熄灭与音乐中断，山门污染与河灯逆流显现。几秒后恢复控制，显示“异变：调查山门”。

熄灭对象是灯会灯笼、灯阵和相关建筑暖光。月光、环境光、路径标记与交互提示保留，保证角色和道路可读。NPC 从生活动作切换为惊讶、避险、警戒或等待。

### 3.3 第一场战斗

两个侵蚀生物出现在去往灯阵的路上。它们可复用一个敌人外形与行为类型，错开攻击，避免初见玩家被同时围攻。

通过简短提示让玩家用到攻击、闪避和净化技能。战斗目标为 20～30 秒内产生一段有完整起承转合的动作展示，实际时长按试玩调整。

### 3.4 三座灵灯

三座灵灯都使用“找到灵石 → 放入灯塔 → 将符文转至对应方向”的交互规则。线索在附近的石刻、灯座或 NPC 对话中出现，使用形状和方向辅助辨认。

第一座负责教学，灵石与线索都在附近；后两座主要通过探索和观察完成。避免重复远距离取物。灯塔附近有安全交互区，解谜过程中不持续刷怪。

| 灵灯 | 解谜重点 | 恢复奖励 |
| --- | --- | --- |
| 广场灵灯 | 学会嵌入灵石与调整符文 | 摊位和建筑暖光恢复，人声回来，茶客与摊主恢复活动 |
| 河岸灵灯 | 观察河岸纹样与符文方向 | 桥灯和河灯恢复，河灯顺流，水面重新出现暖色倒影 |
| 山门灵灯 | 结合已学规则完成最后修复 | 山门结界重新显现，污染收缩，灵兽攻击范围或伤害降低 |

每次成功都先展示区域变化，再提示“引灵灯阵：已恢复 1/3”等进度。玩家能看见变化的发生地点；需要转镜头时短暂引导并允许跳过。

### 3.5 山门净化

Boss 是被污染的守山灵兽。外形应兼具亲近感和守护者的威严；物种与轮廓在概念图阶段确定。污染以青蓝裂纹、异常灵气和动作失控表现，净化后能认出是同一只灵兽。

三座灵灯全部恢复后才能进入净化战。场景中的三束灵光、灵兽身上消退的污染和较弱的攻击明确表现灯阵的作用。第一版不要求玩家在战斗中反复操作灯塔。

灵兽只有冲撞、挥击和一次范围攻击三种主要招式。降低污染值后进入短暂的净化就绪状态，出现交互提示；玩家主动完成净化。终结动画表现污染消散、灵兽平静下来，避免将净化叙述做成普通死亡换一段文字。

### 3.6 灯会继续

净化成功后，山门先恢复，暖光再沿道路与河岸扩散。音乐主题、人声和生活动作逐步回来。

玩家可以走回石桥，与至少一位 NPC 完成一句收尾对话。镜头在确认后拉远，看到山谷中的灯火和顺流河灯，显示结束与重新游玩入口。远处大量灯火用发光素材和实例复用表现，真实光源数量按性能预算控制。

## 4 地图结构

制作一个连贯的宗门地图，包含五个区域：弟子住处、灯会广场、石桥河岸、灯阵步道、山门。瀑布、竹林和山谷作为远景及区域边界。

文字拓扑：住处连接广场；广场连接石桥河岸；河岸连接灯阵步道；步道连接山门。三座灵灯分别位于广场边缘、河岸桥头和山门前，步道提供可回望前一区域的观察点。

地图应满足以下条件：

- 从河岸能看见异常山门，从至少一个高处能回望已恢复的灯会。
- 用地形高差、灯光、道路和建筑轮廓引导，避免只靠任务箭头。
- 桥、石阶、摊位、竹林保留清楚的通行空间，碰撞与视觉边界一致。
- Boss 场地能容纳闪避与范围预警，前景装饰不遮住攻击判定。
- 回程较短，玩家能再次看到熟悉地点的变化。

地图参考图可以由 Meowa 辅助设计，但运行时地形、碰撞、高差、触发区与可交互对象需要在 Three.js 中组装和验证。生成一张完整背景图不能替代可游玩的地图。

## 5 玩法范围

### 5.1 探索与交互

移动、碰撞、角色朝向、对话、摊位浏览、河灯互动、拾取灵石、操作灯塔和净化灵兽构成第一版交互。只在附近存在可交互对象时显示提示，并区分当前目标。

主线任务顺序清晰；可选对话不改变完成条件。背包只承担灵石等任务物品展示，第一版不建设完整装备和经济系统。

### 5.2 基础战斗

| 动作 | 第一版职责 |
| --- | --- |
| 普攻 | 一种清楚的攻击动作，表现命中与敌人受击 |
| 闪避 | 一种短位移，帮助避开可读的预警攻击 |
| 技能 | 一个视觉突出的净化技能，以简单冷却控制使用 |
| 受击 | 动画、音效、短暂保护与生命变化共同反馈 |

不加入蓄能、复杂连击、装备词条、技能树、敌人组合策略或多阶段 Boss。伤害、冷却、闪避保护时间和攻击距离在可玩版本中调节，不提前承诺精确数值。

命中可采用短暂停顿、轻微镜头震动、受击闪光和音效。反馈不能盖过下一次攻击预警；提供减弱震动与闪光的选项。

### 5.3 失败与重试

普通遭遇战失败从战斗前重试；Boss 失败从山门前重试，并保留已完成的三座灯阵进度。失败不会要求重玩灯会开场。

“重新游玩”重置整个事件和地图状态。机关完成、战斗结束和净化事件均只能结算一次；中途重试不能重复生成道具、敌人或恢复奖励。

### 5.4 初版操作建议

| 操作 | 建议按键 |
| --- | --- |
| 移动 | WASD / 方向键 |
| 交互与对话推进 | E |
| 普攻 | J |
| 闪避 | Space |
| 净化技能 | K |
| 任务物品 | Tab |
| 暂停与设置 | Esc |
| 视觉调参面板 | F2 |

按键以最终 UI 提示为准，试玩后可调整。对话、背包、暂停和调参输入占用控制时，不同时驱动角色移动或攻击。

## 6 世界状态与事件控制

整个片段由统一事件进度管理。全局状态负责阶段，局部状态记录每座灵灯、NPC 活动、遭遇战和任务物品。

| 状态 | 进入条件 | 必须联动的内容 |
| --- | --- | --- |
| 灯会 | 开始游戏 | 暖色环境、生活 NPC、正常河灯、灯会音乐 |
| 异变 | 河岸事件触发 | 灯火熄灭、污染出现、NPC 避险、声音与任务改变 |
| 恢复中 | 第一座灯修好 | 已修区域恢复，未修区域保持污染状态 |
| 净化战 | 三座灯全部完成，进入山门 | 灯阵压制污染、灵兽进入战斗、Boss UI 出现 |
| 灯会恢复 | 玩家完成净化 | 灵兽平静、全部区域恢复、收尾目标与音乐回归 |
| 结束 | 玩家完成石桥收尾 | 拉远镜头、结束界面、重玩入口 |

状态切换同时协调光源、发光材质、雾、粒子、河灯运动、NPC 动画、音轨和 UI。局部恢复使用明确区域标识，不能靠全局曝光变亮代替。

录制用的阶段跳转与环境对比独立于正式玩家流程。跳转时必须补齐相应的敌人、灯阵和物品状态；用于美术预览的状态切换不能伪装为完整流程验收。

## 7 像素美术方向

### 7.1 风格原则

东方幻想、夜间灯会、温暖生活气息与冷色灵气污染形成整体辨识度。角色、建筑、道具、地表和 UI 共享像素密度、轮廓语言和色彩关系。

像素风不是将高清图片缩小。素材需要清楚的像素簇、稳定边缘、有限且一致的局部色阶。光照和后处理可以有柔和渐变，但不能把角色和关键道具磨成模糊色块。

### 7.2 三种视觉状态

| 维度 | 灯会 | 异变 | 恢复 |
| --- | --- | --- | --- |
| 主色 | 暖金、朱红、木色，冷月光衬底 | 青蓝、灰紫，少量残余暖光 | 暖色逐区回来，净化灵光收束 |
| 光照 | 灯笼、摊位和建筑有层次 | 熄灯但保留基础可读照明 | 点亮过程可见，倒影随之出现 |
| 雾与粒子 | 轻薄夜雾、萤火与河岸水汽 | 山门污染雾与异常灵气 | 污染消散，生活粒子恢复 |
| 动态 | 河灯顺流、旗帜摆动、NPC 生活动作 | 河灯逆流、NPC 避险、灵兽失控 | 河灯恢复、NPC 活动继续、灵兽平静 |

场景亮度调节、光源开关、材质发光、水面运动、粒子和 NPC 状态是不同职责，需要共同构成世界变化。

### 7.3 初版素材合同

- 主角与普通 NPC 优先采用 64×64 基础设计画布；动作需要空间时使用统一的 128×128 画布。动画角色画布尽量不超过 128×128。
- 主角、NPC、敌人分别统一脚底锚点、站立高度、朝向、身体比例和每帧占位。画布尺寸不等于角色实际身高，导入时按可见身体比例对齐。
- 灵兽优先验证 128×128 画布的可读性；实际体型通过场景缩放与轮廓设计确定。
- 地表优先从 64×64 无缝纹理验证；建筑和大型道具可用更大画布，但像素密度与环境一致。
- 角色与独立道具通常需要透明背景；地表与完整背景按用途保留不透明底色。
- 静态素材使用 PNG；逐帧素材保留透明帧、统一尺寸、帧序和播放数据，再整合图集。
- 素材检查采用原尺寸与整数倍最近邻预览，再在实际游戏大小下确认轮廓和颜色。
- 当前角色渲染存在固定 64 像素采样尺寸；接入更大画布或图集时必须一起更新采样参数、UV 和透明阴影，不能只替换文件。

生成模板的尺寸与输出数量以实际能力合同为准。上述规格是制作基线，选模板或生成前核对，不通过提示词强行覆盖模板限制。

## 8 动画计划

先定角色静态设计、朝向、锚点和比例，再生成动作。初版固定跟随镜头，优先沿用左右镜像显示；纵向移动若明显不自然，再补前后方向，避免一开始要求全部四向动作。

| 对象 | 必需动作 | 制作重点 |
| --- | --- | --- |
| 主角 | 待机、行走、攻击、闪避、施法、受击 | 同一身份与比例；动作准备、命中和收尾可辨认 |
| 生活 NPC | 练剑、喝茶、摆摊、聊天、放灯，以及惊讶或等待 | 短循环可复用，起始时间错开，交互时合理暂停 |
| 侵蚀生物 | 待机、移动、攻击、受击、消散 | 清楚的攻击预警，消散与战斗结束同步 |
| 守山灵兽 | 待机、冲撞、挥击、范围攻击、受击、净化恢复 | 三种攻击可区分，净化后保留角色身份 |
| 环境 | 河灯漂流、旗帜、灯笼摆动、水流、灵灯点亮 | 使用合适的素材动画或程序运动，配合世界状态 |

逐帧动作优先尝试 8～16 帧的短动画，具体帧数与播放速度按动作和所选能力确定。攻击判定绑定动作中的明确时机，不能依赖“视频看起来差不多”。

动画验收检查身份漂移、轮廓抖动、脚底滑动、透明边缘、武器裁切与循环接缝。为动作留出必要运动空间，避免大面积无意义 padding。

## 9 UI 设计

UI 使用与游戏统一的像素装饰，结合纸笺、灵纹、木框或灯会纹样。文本保持清晰，中文字体确认可用授权与字形覆盖；文字由程序排版，不把生成图片中的文字直接作为正式文本。

| 界面 | 第一版内容 |
| --- | --- |
| 开始界面 | 标题、开始、设置；以灯会画面建立第一印象 |
| 探索 HUD | 当前目标、交互提示、任务物品数量 |
| 对话框 | 名称、简短文本、推进提示，可选角色头像 |
| 摊位界面 | 少量商品或灯会道具介绍，可做一次领取，保持浏览轻量 |
| 任务物品面板 | 灵石等少量物品、图标与说明 |
| 战斗 HUD | 主角生命、技能冷却、必要的敌人状态 |
| Boss UI | 灵兽名称与污染值、净化就绪提示 |
| 暂停与设置 | 继续、音量、减弱震动与闪光、重试 |
| 结束界面 | 灯会恢复的收尾文字、重新游玩 |

事件提示“异变：调查山门”突出出现后收为普通任务提示。灯阵恢复信息不长时间挡住环境变化。状态识别同时使用图标、形状与文本，不只依靠颜色。

素材图集需要可读的切片边界、可拉伸面板区域、按钮状态和独立图标。Meowa 的 UI 输出若只有整张图，仍需要提取组件、制作布局和绑定交互。

现有视觉调参面板保留每项独立恢复、配置保存与导入导出功能；左上角 FPS 与平均帧间隔用于开发观察。正式录制可隐藏开发界面。

## 10 音乐与音效

声音与世界状态共同变化。浏览器在玩家点击开始后解锁音频，再进入正式灯会。

| 层次 | 初版需求 |
| --- | --- |
| 环境 | 水流与瀑布、虫鸣、竹林风声、人群底声 |
| 日常动作 | 石地与木桥脚步、练剑、茶杯、放河灯 |
| 交互与 UI | 对话推进、按钮、拾取、灵石嵌入、符文转动、成功提示 |
| 战斗 | 挥击、命中、闪避、施法、敌人消散、灵兽攻击 |
| 事件 | 钟声、熄灯、异常灵气、逐灯恢复、最终净化 |
| 音乐 | 灯会主题、紧张／战斗段落、恢复主题或灯会主题变奏 |

异变时撤掉音乐和人群声，保留风、水声与异常灵气，形成有内容的安静。每座灯修好，相关区域的生活声逐步回来；净化后音乐主题恢复。

短音效考虑重复播放变化与叠加音量；环境和音乐检查循环接缝。按音乐、环境、战斗与 UI 分组控制音量。NPC 第一版以文本对话和短反馈声完成，完整配音作为后续增量。

## 11 第一版资产规模

这是控制成本与工期的最低制作包，最终数量按模板输出和画面验证调整。

| 类别 | 初版规模 |
| --- | --- |
| 地图 | 1 张连续宗门地图，5 个区域，3 座灵灯，1 处山门战斗区 |
| 主角 | 1 个角色设计，6 类核心动作 |
| NPC | 约 4 个基础外形，复用为 6～10 个场景居民 |
| 敌人 | 1 种侵蚀生物，首场战斗出现 2 个实例 |
| Boss | 1 个守山灵兽，污染与净化表现共享身份 |
| 建筑 | 住处、殿宇或广场建筑、山门，按现有几何与新素材组合 |
| 道具 | 灯笼、河灯、摊位、茶具、旗幡、灵石、灯塔与符文等主题包 |
| VFX | 熄灯／污染、普攻命中、净化技能、灵灯恢复、灵兽净化 |
| UI | 1 套统一界面皮肤及任务、物品、技能等必要图标 |
| 音频 | 先覆盖上节列出的事件与动作，再增加变化版本 |

先完成一组代表性资产在同一机位的风格验证，再扩展数量。现有素材可作为占位或可复用资产，采用来源登记区分既有素材、Meowa 生成素材和程序效果。

## 12 Meowa 制作与调用记录

### 12.1 制作流程

1. 确定一张代表性灯会画面的色彩、像素密度与构图，建立参考基线。
2. 定稿主角、灯笼、灯塔、建筑与灵兽的静态设计，确认相互匹配。
3. 制作地图素材与可复用道具；地图布局在运行时验证通行、视线与事件位置。
4. 为已定稿角色生成动画，逐帧检查后接入动作时序。
5. 根据实际界面布局制作 UI 皮肤、组件与图标。
6. 根据游戏动作时长和环境切换制作音效与音乐。
7. 在真实场景中检查一致性，优先修改关键问题，再扩大资产包。

美术、动画、UI、音效和地图素材尽可能使用 Meowa；游戏逻辑、碰撞、灯光、雾、反射、界面行为与事件调度由程序实现。每类资产先定义用途、尺寸、数量、透明度、格式和交付结构，再选择能力或模板。

### 12.2 记录约束

- 所有实际 Meowa 调用，包括生成、编辑、查询、轮询、失败、重试和下载，逐次记录。
- 调用记录保存在项目根目录的独立 `meowa-call-logs/`，不混入设计文档目录。
- 每次调用前记录待调用状态、实际工具与完整参数；实际提示词保留原文、语言和换行，不用摘要代替。
- 调用后补齐实际返回、任务标识、错误、产物和可用预览。未知模型、费用与种子等不编造。
- 每次记录包含 `request.json`、`response.json` 和便于阅读的 `details.md`，必要敏感凭据脱敏。
- 同步到固定阅读页面 [HD 2D Meowa 调用记录](https://chatgpt.com/space/page_a1d8b19baf7c8191913c59c3b647e390)，遵循项目 `AGENTS.md` 的完整规则。
- 候选提示词与实际发送记录分开，不能把策划草案或参考素材标成已经生成的成果。

## 13 技术基础与性能

### 13.1 可复用基础

现有 Three.js 版本已有移动与碰撞、分层地形、像素角色显示、建筑与道具、灯光与阴影、距离与高度雾、水面和反射、瀑布、粒子、天空与远山、后处理及视觉调参界面。

正式逐帧角色动画、对话和任务、战斗、灯阵交互、音频、事件状态控制及净化结局需要新增。当前角色的呼吸与行走挤压效果不能替代正式动作资产。

### 13.2 集成原则

- 将场景布局、资产定义、动画时序和事件配置与运行逻辑分开，便于替换素材和调节流程。
- 状态管理集中协调环境、NPC、音频和 UI；交互对象负责自身行为，避免在各处重复写进度判断。
- 保存原始生成文件与导入资源，保留锚点、动画帧数、帧率、动作事件和来源信息。
- 光照、粒子与反射复用现有能力，按实际可见区域启用昂贵效果。
- 发光灯笼数量与真实动态光源数量分开预算，远景灯火优先复用几何、材质与发光表现。
- 预留开发录制的固定机位、阶段预览和 HUD 隐藏能力，正式通关仍通过正常游戏事件完成。

### 13.3 性能目标与检查

初版参考测试环境以 1280×800、像素比 1 为基准，目标接近稳定 60 FPS；在用户实际设备和分辨率上重新确认，不以此作为现成性能承诺。

FPS 和平均帧间隔使用真实经过时间统计。重点对比广场人群、河岸反射、山门战斗、全灯恢复四种场景，记录分辨率、像素比、硬件、浏览器及效果配置。事件切换与首次播放动画需要额外观察卡顿，避免只看一秒平均值。

高开销效果优先调节反射分辨率与启用范围、真实灯光与阴影数量、粒子数量、景深和接触阴影质量。在保持角色、道路和交互可读的前提下取舍。

## 14 开发里程碑

各阶段以可运行结果验收，不预先给未经估算的完成日期。

| 阶段 | 制作内容 | 通过标准 |
| --- | --- | --- |
| M1 事件核心 | 一个小场景，灯会 → 熄灯 → 点亮一座灵灯，配基础声音 | 玩家可触发；光、雾、声音和至少一位 NPC 联动；三段变化清楚 |
| M2 生活场景 | 完整地图主路径、生活 NPC、对话、河灯与摊位浏览 | 能感到有人生活；能自由移动与交互；异变前有明确记忆点 |
| M3 世界恢复 | 三座灯阵、任务物品、局部恢复、任务进度 | 每灯独立完成且只结算一次；三次反馈不同；路线不拖沓 |
| M4 动作与净化 | 主角动作、首场战斗、灵兽战斗、净化、失败重试 | 动作预警与命中一致；战斗可胜可败；重试保留灯阵；结局能触发 |
| M5 完整演出 | 最终资产、UI、音乐音效、回程与拉远镜头 | 顺利首通约 5～8 分钟，故事与反馈完整，风格一致 |
| M6 录制交付 | 性能检查、回归检查、制作对比、固定机位与记录整理 | 正常路径可通关；高光可重现；配置、来源和调用记录可追溯 |

首个开发目标是 M1，先证明事件具有吸引力，再扩展地图、动作和素材数量。先验证静态角色，再做大量动画；先验证界面布局，再生成整套 UI。

## 16 教学视频与传播镜头

教学主线：一个人借助 AI，把静态场景做成有生命、有事件、有玩家参与的像素游戏世界。

| 镜头 | 对比或高光 | 可解释的制作内容 |
| --- | --- | --- |
| 场景构建 | 空场景／占位 → 完整灯会 | 地图设计、美术生成与运行时组装 |
| 居民活动 | 静态角色 → 练剑、喝茶、摆摊 | 一致角色设计、逐帧动画与活动配置 |
| 界面完善 | 基础布局 → 统一像素 UI | UI 素材与真实交互接入 |
| 声音加入 | 同一镜头静音 → 环境与音乐 | 空间声音、混音与事件切换 |
| 异变 | 同机位灯会全亮 → 灯火熄灭 | 世界状态、灯光、雾、声音与 NPC 联动 |
| 玩家恢复 | 一盏 → 两盏 → 三盏灵灯 | 玩家行为如何逐区改变环境 |
| 净化结局 | 失控灵兽 → 平静守护者 → 山谷灯火 | 动作、VFX、声音与叙事收束 |

制作对比使用相同机位、分辨率和构图，明确素材生成与程序集成各自完成的工作。既有资产、生成资产与后期修整如实标注，不将参考输入当作 Meowa 产物。

实际高光通过可运行 Demo 重现。录制环境预览能辅助演示，但不替代正常通关的视频证据。所有对比优先保留原始录制、配置与阶段文件。

## 17 范围边界与后续决策

第一版包含一个宗门、一个事件、一场小遭遇、三座灵灯、一个守山灵兽和一个净化结局。多章节、开放世界、完整商店经济、装备成长、多人玩法、复杂连击和 Boss 多阶段不进入本次范围。

在各自阶段开始前完成以下决策：

- 美术基线：代表性灯会画面、主角外形、灵兽物种、像素密度与 UI 字体。
- 地图验证：实际区域尺寸、三座灵灯位置、回程长度和可见高光机位。
- 动画验证：素材模板、画布尺寸、必要方向、帧数、动作命中时机。
- 战斗试玩：伤害、冷却、预警、闪避与净化提示是否易懂。
- 制作管理：Meowa 使用预算、资产来源与使用权检查、阶段工期。
- 录制验证：目标设备、正式画质、隐藏调试界面的方式与镜头顺序。

这些决策不改变核心承诺：**玩家参与了一场灯会异变，并让一个有生命的像素世界重新亮起来。**
